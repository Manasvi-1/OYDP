01. Architecture decision ADR-001
Choose a modular monolith: Next.js/TypeScript frontend; one FastAPI deployment with strict internal bounded contexts;
PostgreSQL/PostGIS authoritative data; encrypted object storage for untrusted uploads; bounded background workers and
append-only audit records. All 13 engines share property identity and access decisions. Do not split into microservices without
measured scale/team needs [S01].

03. Key ADR trade-offs
FastAPI provides strong Pydantic and Python GIS/AI interfaces, though TypeScript-to-Python contracts require generated
OpenAPI clients; Next.js supports complex role views but SSR caches must respect tenant isolation. PostgreSQL keeps early
operational complexity low, but GIS ingestion requires specialized CRS expertise. Managed OIDC costs money but reduces
custom password risk. Start with ordinary PostgreSQL search before adding a separate search cluster.

04. Failure and data policies
Idempotency keys prevent repeated invitation/export jobs. Database transactions atomically commit business state with an audit
outbox; async worker sends audit to independent immutable sink. A file is not downloadable until malware result PASS and
object permission evaluation. Data subject requests generate immutable legal-hold exceptions and deletion tombstones rather
than hiding failures. Unknown source availability never becomes a positive legal assertion.

05. Scale triggers and constraints
Do not create individual engine databases at launch. Evaluate sharding, specialized search and independent GIS workers only
when query profiles, volume, team boundaries and SLA breaches justify the separation. Provision regional object storage and DR
only after legal residency/contract checks. Network segmentation and least privilege are mandatory irrespective of scale.
